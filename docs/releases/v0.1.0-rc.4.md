# BYOK Grid 0.1.0-rc.4

<!-- release-version: 0.1.0-rc.4 -->

BYOK Grid is an open-source, fork-first workspace for building data-enrichment
tables and visual, node-based workflows with your own provider credentials.

## Release status

This is a prerelease for evaluation and production-readiness testing, not a
stable production release. It supersedes `v0.1.0-rc.3` after the protected
stable-promotion pull request exposed a shallow-checkout defect in the general
CI workflow. The signed RC.3 tag and its published artifacts remain immutable.

RC.4 changes release machinery and metadata only. Application runtime,
database schema, dependencies, container definitions, and the default
SQLite-native product behavior are unchanged from RC.3.

There is no stable upgrade guarantee before `1.0.0`. Never move or reuse this
version tag; any later release-blocking correction must use a new version.

## Highlights

- Gives the CI job complete Git history when it runs stable release
  verification, allowing the verifier to prove that the observed RC commit is
  an available ancestor of the promotion commit.
- Preserves credential-free checkout while adding a workflow-policy regression
  test that rejects future release-verification jobs with shallow history.
- Triggers a fresh Git-connected Vercel preview for the separate Next.js
  marketing site when the RC.4 pull-request branch is pushed.
- Retains the no-account Next.js application, deterministic local owner,
  SQLite-native Node.js workflow worker, and one authoritative SQLite database.
- Retains the Next.js grid and React Flow editor for published, versioned node
  workflows with filters, enrichment, formulas, writebacks, and signed
  webhooks.
- Keeps remote libSQL, Hatchet, Kubernetes, public ingress, Airbyte, and
  ClickHouse as optional operator choices rather than default infrastructure.
- Continues to publish seven `linux/amd64` and `linux/arm64` images, a Helm
  chart, connector SDK, checksums, SBOMs, provenance, digest-bound smoke
  evidence, and immutable GitHub Release assets through the fail-closed release
  workflow.

The application release version is `0.1.0-rc.4`. The independently versioned
Apache-2.0 connector SDK remains `0.2.0`.

## Verify this release

Treat `IMAGE_DIGESTS.txt` as the authoritative container identity and verify all
downloaded files before deployment:

```text
sha256sum --check SHA256SUMS
npm run release:verify-bundle -- \
  --version 0.1.0-rc.4 \
  --directory /path/to/downloaded-release
```

Then verify GitHub attestations for the release files and exact GHCR digests.
The complete procedure is in the
[release verification guide](https://github.com/mherzog4/byok-grid/blob/v0.1.0-rc.4/docs/VERIFY_RELEASE.md).

## Known limits and production gates

The application intentionally has one local operator boundary, not multi-user
accounts or application-level authorization. Keep ordinary local use on
loopback. Any broader deployment needs an operator-controlled VPN,
identity-aware proxy, or equivalent access boundary, plus unique encryption
secrets, backups, monitoring, and an incident owner.

The default stable-product evidence is described in the
[production-readiness ledger](https://github.com/mherzog4/byok-grid/blob/v0.1.0-rc.4/docs/PRODUCTION_READINESS.md).
Deployments that claim Hatchet, remote libSQL, Kubernetes, public ingress,
Airbyte, ClickHouse, or a specific capacity envelope must also run the matching
optional runbooks. Report defects through the
[structured issue chooser](https://github.com/mherzog4/byok-grid/issues/new/choose)
and disclose vulnerabilities according to
[SECURITY.md](https://github.com/mherzog4/byok-grid/blob/v0.1.0-rc.4/SECURITY.md).
